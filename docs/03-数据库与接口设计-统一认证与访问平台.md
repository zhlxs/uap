# 统一认证与访问平台数据库与接口设计

## 1. 设计原则

- 用户、账号、外部身份分离。
- 应用、协议客户端、密钥分离。
- 会话、Token、授权码生命周期清晰。
- 密码、client_secret、authorization_code、refresh_token 只存 hash。
- 审计日志不可被普通业务流程删除。
- 所有核心表包含 created_at、updated_at，必要时包含 created_by、updated_by。
- 所有面向列表的管理查询必须支持分页。
- 所有外部 API 返回稳定 error_code。

## 2. 命名约定

- 身份域表前缀：iam_
- 认证授权域表前缀：auth_
- 应用域表前缀：uap_
- 策略域表前缀：policy_
- 审计域表前缀：audit_
- 安全事件表前缀：security_

字段约定：

```text
id: varchar(64) 或 bigint，按公司规范选择
status: varchar(32)
created_at: timestamp
updated_at: timestamp
deleted_at: timestamp，可选
version: bigint，乐观锁可选
```

## 3. 核心实体关系

```text
iam_user 1 - n iam_account
iam_user 1 - n iam_identity_binding
iam_department 1 - n iam_user
iam_group n - n iam_user
iam_role n - n iam_permission
iam_user n - n iam_role
uap_application 1 - n uap_oauth_client
uap_application 1 - n uap_saml_client
uap_application 1 - n uap_cas_service
auth_session 1 - n auth_refresh_token
uap_oauth_client 1 - n auth_authorization_code
uap_oauth_client 1 - n auth_access_token
```

## 7. 权限域表

权限中心支持四种产品接入模式：

```text
sso_only:
仅统一登录。UAP 只负责身份认证和 SSO，业务系统自行管理访问控制和业务权限。

delegated:
业务系统自管权限，UAP 下发应用角色、scope、permission code。
业务系统自行解释这些角色和权限码，并控制菜单、按钮、接口和数据权限。

centralized:
UAP 统一托管权限。UAP 管理菜单、按钮、API、数据范围和角色授权。
业务系统通过 UAP 权限接口获取权限结果或进行权限判定。

hybrid:
混合模式。菜单、按钮、API、数据权限可以分别选择由 UAP 管理或业务系统管理。
```

推荐落地策略：

- 老系统优先使用 sso_only 或 delegated，降低改造成本。
- 新系统和统一平台优先使用 centralized，提升治理能力。
- 数据权限复杂的系统优先使用 hybrid。
- UAP 不直接拼业务 SQL，只返回数据权限范围和条件。
- 高风险 API 不只依赖前端按钮隐藏，必须后端鉴权。

底层能力开关：

```text
app_access_control:
是否由 UAP 控制谁能访问应用。

role_permission_enabled:
是否启用应用角色、scope、permission code。

resource_managed_by_uap:
菜单、按钮、API 是否由 UAP 管理。

data_scope_managed_by_uap:
数据权限是否由 UAP 管理。

permission_delivery:
权限通过 Token 下发，还是通过权限接口查询。
```

权限模式与能力开关映射：

| 模式 | 应用访问控制 | 角色/权限码 | 菜单/按钮/API 托管 | 数据权限托管 | 权限交付 |
| --- | --- | --- | --- | --- | --- |
| sso_only | 可选 | 否 | 否 | 否 | identity claims |
| delegated | 是 | 是 | 否 | 否 | token claims 或 permission API |
| centralized | 是 | 是 | 是 | 是 | permission API + cache |
| hybrid | 是 | 是 | 部分 | 部分 | token claims + permission API |

要求：

- 返回字段受 scope 控制，没有对应 scope 不返回敏感字段。
- 手机号、邮箱、工号等字段按安全策略脱敏或隐藏。
- 列表接口必须分页。
- 查询行为写入审计日志。
- 写接口默认不开放；用户和组织变更优先通过 HR、SCIM 或管理员后台完成。

```http
POST /api/developer/apps/{id}/resources/validate
```

接入原则：

- 标准协议优先，SDK 只是提效工具。
- 业务系统可以只使用标准 OIDC、OAuth2、SAML、CAS 客户端库接入。
- UAP SDK 可选，用于封装登录回调、用户信息解析、Token 校验、权限查询、权限注解和登出。
- 老系统可以使用网关或代理接入，但必须保证 Header 只能由可信网关注入。

Spring Boot 标准库接入配置示例：

```yaml
spring:
  security:
    oauth2:
      client:
        registration:
          uap:
            client-id: finance-web
            client-secret: ${UAP_CLIENT_SECRET}
            scope: openid, profile, email
            authorization-grant-type: authorization_code
            redirect-uri: "{baseUrl}/login/oauth2/code/uap"
        provider:
          uap:
            issuer-uri: https://uap.company.com
```

Java SDK 可选接入配置示例：

```yaml
uap:
  issuer-uri: https://uap.company.com
  client-id: finance-web
  client-secret: ${UAP_CLIENT_SECRET}
  scopes:
    - openid
    - profile
    - email
  permissions:
    enabled: true
    cache-ttl-seconds: 300
```

Maven 依赖示例：

```xml
<dependency>
  <groupId>com.company.uap</groupId>
  <artifactId>uap-spring-boot-starter</artifactId>
  <version>1.0.0</version>
</dependency>
```

网关 Header 透传示例：

```text
X-UAP-User-Id: user_123
X-UAP-Username: zhangsan
X-UAP-Email: zhangsan@company.com
X-UAP-Department-Id: dept_100
X-UAP-Roles: employee,department_approver
```

网关接入安全要求：

- 业务系统必须只接受来自可信网关的请求。
- 外部网络不能直接访问业务系统并伪造 Header。
- 高敏系统不建议只依赖 Header 透传。
- Header 注入、用户映射和登录结果必须写入审计日志。

权限接入指南应覆盖：

- sso_only 接入方式。
- delegated 接入方式。
- centralized 接入方式。
- hybrid 接入方式。
- 前端菜单和按钮控制示例。
- 后端 API 鉴权示例。
- 数据权限条件转换示例。
- 权限缓存和 permission_version 使用方式。

## 15. 数据保留建议

- 登录日志：至少 180 天，安全要求高时 1 年以上。
- 管理员操作日志：至少 1 年。
- 安全事件：至少 1 年。
- Token 记录：过期后保留 7 到 30 天，用于追溯和重放检测。
- 审计归档：进入低成本存储，不允许普通管理员删除。

## 16. 评审关注点

- 主键采用 varchar 还是 bigint。
- 数据库选 PostgreSQL 还是 MySQL。
- JSON 字段是否符合公司数据库规范。
- refresh_token 是否所有客户端都允许。
- access_token 默认 JWT 还是 opaque token。
- 审计日志是否需要独立库或独立存储。
- 多租户字段是否第一阶段启用。
- centralized 是否进入第一期。
- 老系统默认采用 sso_only、delegated、centralized 还是 hybrid。
- 四种权限模式是否明确为产品预设，而不是四套独立实现。
- permission_capabilities_json 的能力开关是否满足接入差异。
- 菜单、按钮、API、数据资源是否全部由 UAP 统一注册。
- 数据权限由 UAP 返回条件，还是业务系统自行维护。
- 权限变更是否要求实时生效。
- 权限信息是否进入 Token，还是通过权限接口实时查询。
- 业务系统权限缓存 TTL 和 permission_version 机制是否满足安全要求。
