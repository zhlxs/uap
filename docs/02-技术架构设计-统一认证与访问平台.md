# 统一认证与访问平台技术架构设计

## 1. 架构目标

UAP 是公司级身份基础设施，架构设计需要满足以下目标：

- 标准协议优先，核心认证授权基于 OIDC、OAuth2、SAML、CAS。
- 认证、授权、会话、Token、权限、审计职责清晰分层。
- 支持多应用、多协议、多身份源接入。
- 默认安全，避免自定义协议和弱安全模式。
- 支持水平扩展、高可用、灰度发布和故障降级。
- 支持可观测、可审计、可追溯。
- 支持未来多租户、插件化、SDK 和企业集成扩展。

## 4. 服务划分

### 4.1 初始部署形态

建议初期采用模块化单体或少量服务，而不是过早拆成大量微服务。

推荐进程：

```text
uap-auth-server
- 登录
- OIDC / OAuth2
- Token
- Session
- MFA

uap-admin-api
- 用户管理
- 应用管理
- 策略管理
- 审计查询

uap-console
- 管理后台
- 开发者门户

uap-worker
- 用户同步
- 日志异步写入
- 风险分析
- Webhook 投递
```

原因：

- 认证链路对一致性、事务和故障定位要求高。
- 过早微服务化会增加分布式事务、链路延迟和排障成本。
- 模块化单体可以先保证领域边界，后续按压力和团队边界拆分。

### 4.2 后续可拆服务

```text
identity-service
application-service
policy-service
audit-service
risk-service
connector-service
notification-service
```

拆分条件：

- 单模块负载明显独立。
- 团队边界清晰。
- 数据边界稳定。
- 有独立扩缩容需求。

## 5. 业务系统接入形态

### 5.1 标准协议接入

标准协议接入是默认和首选方式。业务系统不应被强制绑定 UAP 专用 SDK。

推荐接入方式：

```text
新 Web 系统：
OIDC Authorization Code + PKCE。

SPA：
OIDC Authorization Code + PKCE，不使用 Implicit Flow。

后端服务：
OAuth2 Client Credentials。

第三方 SaaS：
SAML 或 OIDC。

老 Java Web：
CAS 或 OIDC。
```

只要 UAP 按标准暴露以下端点，业务系统即可使用标准库接入：

```text
/.well-known/openid-configuration
/oauth2/authorize
/oauth2/token
/oauth2/jwks
/oauth2/userinfo
/oauth2/revoke
/oauth2/introspect
```

### 5.2 Java SDK / Spring Boot Starter

UAP 可以提供 Java SDK 或 Spring Boot Starter，但它是可选增强能力，不是强制依赖。

建议 Maven 坐标：

```xml
<dependency>
  <groupId>com.company.uap</groupId>
  <artifactId>uap-spring-boot-starter</artifactId>
  <version>1.0.0</version>
</dependency>
```

SDK 职责：

- 自动装配 UAP issuer、client_id、client_secret、scope。
- 封装 OIDC 登录和回调处理。
- 封装用户信息解析。
- 封装 Token 校验和 JWKS 缓存。
- 封装登出。
- 封装权限接口调用。
- 提供权限注解，如 `@RequirePermission`。
- 提供当前用户上下文工具。

SDK 不应承担：

- 自定义私有登录协议。
- 绕过 OIDC/OAuth2 标准流程。
- 替业务系统拼接数据权限 SQL。
- 强制所有 Java 系统依赖 SDK 才能接入。

### 5.3 前端 SDK

前端 SDK 可用于 SPA 场景，职责包括：

- 发起 Authorization Code + PKCE 登录。
- 管理 state、nonce、code_verifier。
- 处理登录回调。
- 获取当前用户信息。
- 调用权限接口获取菜单和按钮权限。
- 处理前端登出。

前端 SDK 不应在浏览器中保存 client_secret。

### 5.4 网关或代理接入

对无法快速改造的老系统，可以通过网关、反向代理或 OAuth2 Proxy 接入。

典型方式：

```text
User -> Gateway -> UAP Login -> Gateway injects headers -> Legacy App
```

可信 Header 示例：

```text
X-UAP-User-Id
X-UAP-Username
X-UAP-Email
X-UAP-Department-Id
X-UAP-Roles
```

安全要求：

- 老系统只能被可信网关访问。
- 外部请求不能直接访问老系统并伪造 Header。
- Header 必须经过签名或网关网络隔离保护。
- 网关注入 Header 的行为必须审计。
- 高敏系统不建议只依赖 Header 透传。

## 6. 核心领域设计

### 6.1 Identity Service

职责：

- 用户、账号、组织、部门、岗位、用户组管理。
- 外部身份绑定。
- 账号状态和生命周期。
- 身份源同步。

关键原则：

- User 与 Account 分离。
- User 表达自然人或企业身份主体。
- Account 表达登录凭据。
- IdentityBinding 表达外部身份源身份。

### 6.2 Application Service

职责：

- 应用注册。
- OIDC/OAuth2 Client 管理。
- SAML SP 管理。
- CAS Service 管理。
- 应用密钥管理。
- 应用策略绑定。
- 接入测试和诊断。

关键原则：

- 每个接入系统必须有明确 Owner。
- redirect_uri 必须精确匹配。
- secret 只展示一次，后续只允许轮换。
- 测试环境和生产环境配置隔离。

### 6.3 Authentication Service

职责：

- 登录流程编排。
- 密码认证。
- 短信、邮箱、扫码认证。
- 外部 IdP 认证。
- MFA 挑战。
- 登录失败处理。

关键原则：

- 认证因子插件化。
- 登录流程由策略驱动。
- 认证结果写入 Authentication Context。
- 避免在认证流程中耦合具体应用逻辑。

### 6.4 Authorization Service

职责：

- 授权请求校验。
- Scope 校验。
- 用户 Consent，可选。
- 应用访问授权。
- 角色和权限映射。

关键原则：

- 认证证明用户是谁。
- 授权决定用户能访问什么。
- 不把业务系统内部复杂权限强行塞入 OIDC 基础 Token。

### 6.5 Token Service

职责：

- 颁发 authorization_code。
- 颁发 access_token。
- 颁发 refresh_token。
- 颁发 id_token。
- Token 撤销。
- Token introspection。
- JWKS 暴露。
- 密钥轮换。

关键原则：

- authorization_code、refresh_token 存储 hash。
- access_token 默认短有效期。
- refresh_token 轮换。
- JWT 包含 aud、iss、sub、exp、iat、jti、scope。
- ID Token 只用于身份声明，不作为 API 访问令牌。

### 6.6 Session Service

职责：

- UAP 全局会话。
- 设备会话。
- 单点登录。
- 单点退出。
- 强制下线。

关键原则：

- 区分 UAP Global Session、Client Session、Token Session。
- Cookie 使用 HttpOnly、Secure、SameSite。
- 会话与 Token 可关联撤销。

### 6.7 Policy Service

职责：

- 密码策略。
- MFA 策略。
- 会话策略。
- Token 策略。
- IP 策略。
- 设备策略。
- 风险策略。

策略输入：

```text
subject: user, account, role, group, department
resource: application, scope, operation
environment: ip, geo, device, browser, time, network
behavior: failed_count, new_device, impossible_travel, token_reuse
```

策略输出：

```text
allow
deny
require_mfa
require_password_change
limit_session_ttl
limit_token_ttl
notify
lock_account
```

### 6.8 Audit Service

职责：

- 登录日志。
- 授权日志。
- 管理操作日志。
- 安全事件。
- 策略命中日志。
- 审计查询和导出。

关键原则：

- 认证主链路不应被日志系统阻塞。
- 本地事务记录关键审计事件，异步扩展到日志平台。
- 审计日志不可被普通管理员删除。
- 敏感字段脱敏。

## 7. 协议设计

### 7.1 OIDC / OAuth2

必须支持：

```text
Authorization Code + PKCE
Client Credentials
Refresh Token
Token Revocation
Token Introspection
JWK Set
OpenID Provider Configuration
UserInfo
RP-Initiated Logout，可选
```

禁止或默认禁用：

```text
Implicit Flow
Password Grant
通配符 redirect_uri
不校验 state 的授权请求
不校验 nonce 的 OIDC 请求
```

端点：

```text
GET  /.well-known/openid-configuration
GET  /oauth2/authorize
POST /oauth2/token
POST /oauth2/revoke
POST /oauth2/introspect
GET  /oauth2/jwks
GET  /oauth2/userinfo
GET  /oauth2/logout
```

### 7.2 SAML 2.0

支持：

```text
IdP Metadata
SP Metadata import
HTTP-Redirect Binding
HTTP-POST Binding
Signed Assertion
Encrypted Assertion，可选
NameID mapping
Attribute mapping
Single Logout，可选
```

安全要求：

- 校验 SP Entity ID。
- 校验 ACS URL。
- Assertion 必须有有效期。
- Response ID 防重放。
- 证书轮换有过渡期。

### 7.3 CAS

支持：

```text
/cas/login
/cas/logout
/cas/serviceValidate
/cas/p3/serviceValidate
```

安全要求：

- service 白名单。
- Ticket 短有效期且一次性使用。
- 登出通知可配置。

### 7.4 LDAP / AD

支持模式：

```text
认证代理：用户密码由 AD 校验。
数据同步：用户、部门、用户组同步到 UAP。
混合模式：认证代理 + 本地缓存身份。
```

要求：

- 支持 LDAPS。
- 支持连接池。
- 支持同步字段映射。
- 支持失败重试和同步报告。

### 7.5 SCIM

用于身份生命周期自动化。

支持：

```text
Users
Groups
Create
Read
Update
Delete / Deactivate
Patch
```

## 8. 安全架构

### 8.1 密码安全

- 使用 Argon2id、bcrypt 或 scrypt。
- 每个密码独立 salt。
- 支持密码泄露库检查。
- 支持密码历史。
- 管理员重置密码后要求用户首次登录改密。
- 登录失败按账号、IP、设备多维限流。

### 8.2 Token 安全

- access_token 短有效期。
- refresh_token 轮换。
- refresh_token 存储 hash。
- 检测 refresh_token 重放。
- 支持 revoke。
- 支持 jti。
- 支持 audience 限制。

### 8.3 Client 安全

- client_secret 存储 hash。
- secret 只展示一次。
- 支持 secret 轮换。
- 支持 private_key_jwt。
- 管理端修改 redirect_uri 需要审计。

### 8.4 Cookie 与浏览器安全

- HttpOnly。
- Secure。
- SameSite=Lax 或 Strict，按场景配置。
- CSRF 防护。
- CSP。
- HSTS。
- X-Frame-Options 或 frame-ancestors。

### 8.5 密钥管理

- JWT 使用 RSA 或 ECDSA。
- JWKS 暴露公钥。
- kid 标识密钥版本。
- 支持 active、next、retired 状态。
- 支持无中断轮换。
- 私钥放 KMS、HSM 或安全配置中心。

## 9. 高可用架构

### 9.1 无状态服务

认证服务实例不保存本地会话状态。会话状态存储在 Redis 或数据库中。

### 9.2 Redis

用途：

- 登录会话缓存。
- 授权请求临时状态。
- 限流计数。
- 短期风险状态。
- 分布式锁，可选。

要求：

- Redis Sentinel 或 Cluster。
- 设置合理 TTL。
- 关键数据不能只存在 Redis。

### 9.3 数据库

用途：

- 用户和组织。
- 应用配置。
- 策略配置。
- Token 和会话持久状态。
- 审计索引。

要求：

- 主从或高可用集群。
- 关键表索引优化。
- 审计日志分区。
- 定期备份和恢复演练。

### 9.4 MQ

用途：

- 审计异步扩散。
- 风险事件处理。
- 用户同步任务。
- Webhook 投递。
- 通知发送。

### 9.5 降级策略

- 审计扩展系统异常时，核心登录不应失败，但本地关键审计必须落库。
- 短信服务异常时，允许用户使用备用 MFA。
- LDAP 异常时，按安全策略决定是否允许短期缓存认证。
- 风控服务异常时，默认使用保守策略。
- 开发者门户异常不影响认证主链路。

## 13. 关键技术决策

### 13.1 是否使用 Spring Authorization Server

建议使用。

理由：

- OAuth2/OIDC 底层复杂，安全风险高。
- 标准框架可以减少协议实现错误。
- 企业差异化应放在身份、策略、审计、接入体验上。

### 13.2 Access Token 使用 JWT 还是 opaque token

建议默认 JWT，敏感应用允许 opaque token。

JWT 优点：

- 业务服务可本地验签。
- 性能好。
- 适合内部微服务。

opaque token 优点：

- 可即时撤销。
- 信息不暴露给客户端。
- 适合高安全场景。

### 13.3 权限中心采用轻模式还是强模式

建议先轻模式，保留强模式扩展。

轻模式：

- UAP 管应用访问、角色、scope。
- 业务系统管内部细权限。

强模式：

- UAP 管菜单、按钮、API、数据权限。
- 适合新建统一业务平台，不适合强行改造所有历史系统。

## 14. 风险与应对

- 协议实现错误：使用成熟框架，补充协议测试。
- 外部身份源不稳定：增加缓存、重试、降级和告警。
- 审计量过大：冷热分离、分区表、异步写入。
- Token 无法即时撤销：缩短 TTL，增加撤销列表或 introspection。
- 接入成本高：建设开发者门户、示例应用和诊断工具。
- 管理员误操作：敏感操作二次确认、二次认证和审计。

## 15. 评审关注点

- 初期采用模块化单体是否符合团队能力。
- OIDC、SAML、CAS 的协议优先级是否匹配现有系统。
- JWT 与 opaque token 的默认策略是否合适。
- LDAP/AD 和 HR 系统哪个作为主数据源。
- 审计日志保留周期和存储成本。
- 高可用目标和预算是否匹配。
