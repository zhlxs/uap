# 统一认证与访问平台 PRD

## 1. 文档信息

- 产品名称：UAP，Unified Access Platform
- 产品定位：企业级统一身份认证、单点登录、应用接入与访问治理平台
- 目标读者：产品负责人、研发负责人、架构师、安全负责人、运维负责人、业务系统接入方
- 文档版本：v0.1
- 状态：评审稿

## 2. 背景与问题

企业内部通常存在多个 Web 应用、管理后台、移动端、API 服务和第三方 SaaS。各系统如果各自实现登录、账号、权限和审计，会带来以下问题：

- 用户需要重复登录，体验差。
- 账号生命周期分散，离职、调岗、禁用无法及时生效。
- 各业务系统认证安全水平不一致。
- 应用接入依赖人工沟通，缺少标准协议和自助文档。
- 登录、授权、管理员操作缺少统一审计。
- 安全策略无法按用户、应用、设备、网络环境统一治理。
- 认证平台高可用和故障降级能力不足，影响全公司业务连续性。

UAP 的目标是建设公司级身份基础设施，而不是单一登录页。

## 3. 产品目标

### 3.1 核心目标

- 提供标准化 SSO 能力，让内部和外部 Web 应用可以通过 OIDC、OAuth2、SAML、CAS 等协议接入。
- 建立统一身份中心，管理用户、组织、部门、岗位、用户组、账号和外部身份绑定。
- 建立应用中心，支持应用自助注册、配置、测试、上线和审计。
- 建立安全策略中心，实现 MFA、会话、密码、IP、设备、风险登录等策略治理。
- 建立审计与风控能力，对登录、授权、管理操作和安全事件进行统一记录与告警。
- 提供开发者门户和 SDK 示例，降低接入成本。
- 支持高可用部署、可观测性、密钥轮换和运维治理。

### 3.2 体验目标

- 普通业务系统开发者能在 30 分钟内完成测试环境 OIDC 接入。
- 业务应用接入问题可以通过管理后台和开发者门户自助排查。
- 用户一次登录后，在授权范围内访问多个应用无需重复登录。
- 高风险场景下安全增强应明确、可解释，不应无提示失败。
- 管理员可以快速定位用户登录失败、Token 失效、回调地址错误、权限缺失等问题。

### 3.3 非目标

- 第一阶段不替代所有业务系统内部细粒度权限。
- 不自定义私有 SSO 协议作为主要接入方式。
- 不将 UAP 作为业务数据权限的唯一强制中心，除非业务系统明确选择强权限模式。
- 不在认证核心流程内依赖不稳定外部系统作为单点。

## 4. 用户角色

### 4.1 终端用户

公司员工、外包人员、合作伙伴或客户，使用 UAP 登录各业务系统。

核心诉求：

- 登录简单、安全、稳定。
- 一次登录，多系统免登。
- 可以查看和管理自己的登录设备、MFA、绑定账号。

### 4.2 应用开发者

负责业务系统接入 UAP 的研发人员。

核心诉求：

- 有清晰的协议文档、示例代码和 SDK。
- 可以自助创建测试应用。
- 可以快速排查回调地址、Token、Scope、SAML Metadata 等接入问题。

### 4.3 应用负责人

负责某个业务应用的产品、研发或系统 Owner。

核心诉求：

- 管理应用的登录方式、访问范围、权限映射和安全策略。
- 查看应用登录情况和接入健康状态。
- 管理应用密钥和回调地址。

### 4.4 UAP 管理员

负责统一认证平台配置和日常管理。

核心诉求：

- 管理用户、组织、应用、权限、策略和审计。
- 处理账号锁定、登录异常、权限异常和安全告警。
- 对高权限操作进行审计和追溯。

### 4.5 安全管理员

负责安全策略、风险治理、审计合规和应急响应。

核心诉求：

- 统一 MFA、密码、设备、网络、风险登录策略。
- 查看和处置高风险登录、Token 重放、撞库、管理员异常操作。
- 对接 SIEM、告警和合规报表。

### 4.6 运维管理员

负责 UAP 部署、监控、容量、备份和故障恢复。

核心诉求：

- 获取健康检查、指标、日志、链路追踪。
- 支持高可用、灰度发布、备份恢复和密钥轮换。
- 故障时有明确降级和应急方案。

## 5. 核心业务场景

### 5.1 标准 Web 应用单点登录

业务应用使用 OIDC Authorization Code + PKCE 接入 UAP。

流程：

1. 用户访问业务应用。
2. 业务应用发现本地未登录，跳转 UAP 授权端点。
3. UAP 检查全局会话。
4. 未登录则展示登录页，已登录则直接授权。
5. UAP 回调业务应用，返回 authorization code。
6. 业务应用后端换取 Token。
7. 业务应用获取用户信息并创建本地会话。

验收标准：

- 支持标准 OIDC Discovery。
- 支持 PKCE。
- redirect_uri 精确匹配。
- 支持 state 和 nonce 校验。
- 登录成功、失败和授权行为写入审计日志。

### 5.2 SPA 单页应用登录

SPA 使用 Authorization Code + PKCE，不使用 Implicit Flow。

验收标准：

- 禁止 Implicit Flow。
- 禁止在前端保存 client_secret。
- access_token 短有效期。
- refresh_token 根据安全策略决定是否允许下发给 SPA。
- 支持 CORS 白名单。

### 5.3 后端服务访问 API

后端服务使用 Client Credentials 获取访问令牌。

验收标准：

- 支持 client_secret_basic、client_secret_post、private_key_jwt 中至少一种客户端认证方式。
- 支持 scope 和 audience 限制。
- 支持 Token introspection 或 JWT 验签。
- 客户端密钥不明文存储。

### 5.4 SAML 应用接入

兼容旧系统、国外 SaaS 或标准企业应用。

验收标准：

- 支持 IdP Metadata。
- 支持 SP Metadata 导入。
- 支持 Assertion 签名。
- 支持 NameID 和属性映射。
- 支持 SAML Response 防重放。

### 5.5 CAS 应用接入

兼容历史 Java Web 系统。

验收标准：

- 支持 /login、/logout、/serviceValidate。
- 支持 service 白名单。
- 支持 CAS 登录日志和登出通知。

### 5.6 外部身份源同步

从 LDAP、AD、HR 系统、企业微信、钉钉、飞书等同步用户和组织。

验收标准：

- 支持全量同步和增量同步。
- 支持字段映射。
- 支持禁用、离职、调岗、部门变更。
- 支持同步预览和失败重试。
- 同步操作写入审计日志。

### 5.7 MFA 与风险登录

针对管理员、外网访问、敏感应用和异常设备强制增强认证。

验收标准：

- 支持 TOTP、短信、邮箱、WebAuthn 中至少两种 MFA。
- 支持按用户、角色、应用、IP、设备、风险等级配置 MFA 策略。
- 支持备用恢复码。
- MFA 绑定、解绑、重置需要审计。

### 5.8 会话与强制下线

用户和管理员可以管理在线会话。

验收标准：

- 用户可以查看自己的在线设备和登录时间。
- 用户可以主动下线指定设备。
- 管理员可以强制下线用户。
- 密码修改、账号禁用、风险事件触发后可以撤销相关会话和 Token。

## 6. 功能需求

### 6.1 登录门户

- 支持账号密码登录。
- 支持短信、邮箱、扫码、外部身份源登录。
- 支持 MFA 挑战。
- 支持密码找回。
- 支持账号锁定提示。
- 支持登录失败统一错误提示，避免账号枚举。
- 支持品牌化配置，包括 Logo、标题、主题色和登录页公告。

### 6.2 用户与组织管理

- 用户创建、编辑、禁用、解锁、重置密码。
- 组织、部门、岗位管理。
- 用户组管理。
- 用户与部门、岗位、用户组关系管理。
- 外部身份绑定管理。
- 账号生命周期管理。
- 批量导入、导出。

### 6.3 应用管理

- 创建 OIDC、OAuth2、SAML、CAS 应用。
- 配置 client_id、client_secret、redirect_uri、logout_uri、scope、grant_type。
- 支持密钥生成、轮换、禁用。
- 支持应用 Owner。
- 支持应用接入状态、最近登录、失败原因。
- 支持应用级登录策略、MFA 策略、Token 策略。
- 支持测试环境和生产环境配置隔离。

### 6.4 权限管理

- 平台管理员角色。
- 应用访问授权。
- 用户、部门、用户组、角色维度授权。
- Scope 管理。
- 应用角色映射。
- 可选的菜单、按钮、API 权限模型。

权限管理模式：

```text
sso_only:
仅统一登录。UAP 只负责身份认证和 SSO，业务系统自行管理访问控制和业务权限。

delegated:
业务系统自管权限，UAP 下发应用角色、scope、permission code。
业务系统自行解释这些角色和权限码，并控制菜单、按钮、接口和数据权限。

centralized:
UAP 统一托管权限。UAP 管理菜单、按钮、API、数据范围和角色授权。
业务系统通过 UAP 权限接口获取权限结果或进行权限判定。

hybrid:
混合模式。菜单、按钮、API、数据权限可以分别选择由 UAP 管理或业务系统管理。
```

设计原则：

- 权限模式是应用接入时的产品预设，由应用负责人显式选择。
- 系统可以根据应用类型和协议给出推荐模式，但不自动决定。
- 安全管理员可以对高敏应用强制指定权限模式。
- 四种模式不对应四套独立实现，底层由一套权限模型和能力开关组合。
- 老系统优先使用 sso_only 或 delegated，降低接入成本。
- 新系统和统一管理后台优先使用 centralized。
- 数据权限复杂的系统优先使用 hybrid。

底层能力开关：

```text
app_access_control:
是否由 UAP 控制谁能访问应用。

role_permission_enabled:
是否启用应用角色、scope、permission code。

resource_managed_by_uap:
菜单、按钮、API 是否由 UAP 管理。

data_scope_managed_by_uap:
数据权限是否由 UAP 管理。

permission_delivery:
权限通过 Token 下发，还是通过权限接口查询。
```

### 6.5 策略中心

- 密码策略。
- 登录失败锁定策略。
- MFA 策略。
- IP 黑白名单。
- 设备信任策略。
- 会话生命周期策略。
- Token 生命周期策略。
- 高风险登录策略。

### 6.6 安全中心

- 在线会话查看和撤销。
- Token 查看和撤销。
- 密钥管理和轮换。
- 风险事件查看和处置。
- 高风险 IP 管理。
- 管理员敏感操作二次验证。

### 6.7 审计中心

- 登录日志。
- 授权日志。
- 管理员操作日志。
- 安全事件日志。
- 策略命中日志。
- 支持搜索、筛选、导出。
- 支持 Webhook、SIEM、消息队列对接。

### 6.8 开发者门户

- OIDC 接入文档。
- OAuth2 接入文档。
- SAML 接入文档。
- CAS 接入文档。
- Java、Node.js、React、Vue 示例。
- Java Spring Boot Starter，可选。
- 前端 SDK，可选。
- 网关或代理接入指南。
- Token 解析工具。
- JWKS 查看工具。
- 回调地址测试工具。
- SAML Metadata 下载。
- 常见错误码和排查建议。

接入原则：

- 标准协议优先，SDK 只是提效工具。
- 任何支持 OIDC、SAML、CAS 的业务系统，都应能不依赖 UAP 专用 SDK 完成接入。
- Java 业务系统可以使用 Spring Security OAuth2 Client 等标准库接入。
- UAP SDK 不替代标准协议，只封装登录回调、用户信息解析、Token 校验、权限查询、权限注解和登出等常用能力。
- 老系统可以通过网关、代理或 Header 透传方式接入，但必须保证 Header 只能由可信网关注入。

## 7. 非功能需求

### 7.1 安全

- 密码使用 Argon2id、bcrypt 或 scrypt 强哈希。
- 密码、client_secret、refresh_token、authorization_code 不明文存储。
- Cookie 使用 HttpOnly、Secure、SameSite。
- 禁用 OAuth Implicit Flow。
- redirect_uri 精确匹配。
- 支持 Refresh Token 轮换和重放检测。
- 支持密钥轮换和 JWKS。
- 高权限管理员强制 MFA。
- 所有敏感管理操作写入审计日志。

### 7.2 可用性

- 支持多实例无状态部署。
- 支持数据库高可用。
- 支持 Redis 高可用。
- 支持服务健康检查。
- 支持灰度发布。
- 目标可用性：99.9% 起步，核心场景建议 99.95%。

### 7.3 性能

- 登录接口 P95 小于 300ms，不含外部短信、LDAP、第三方 IdP。
- Token 颁发 P95 小于 100ms。
- JWKS 获取 P95 小于 50ms。
- Token 本地 JWT 验签 P95 小于 10ms。
- 管理后台列表查询支持分页和索引优化。

### 7.4 可观测性

- 暴露 Prometheus 指标。
- 接入集中日志。
- 支持 trace_id 贯穿登录、授权、Token、审计链路。
- 支持核心错误码统计。
- 支持登录成功率、失败率、MFA 成功率、Token 刷新失败率监控。

### 7.5 合规与审计

- 审计日志保留周期可配置。
- 关键日志防篡改。
- 支持管理员操作追溯。
- 支持导出审计报表。
- 支持数据脱敏展示。

## 8. 关键指标

- 日登录成功率。
- 登录失败原因分布。
- 应用接入数量。
- OIDC/SAML/CAS 接入占比。
- 平均接入耗时。
- MFA 覆盖率。
- 高风险登录处置率。
- Token 撤销延迟。
- 审计日志完整率。
- 系统可用性。

## 9. 版本规划

### 9.1 第一阶段：认证协议核心

- 用户、组织、应用基础模型。
- OIDC Authorization Code + PKCE。
- OAuth2 Client Credentials。
- JWT、JWKS、Refresh Token 轮换。
- 应用管理后台。
- 权限模式支持 sso_only 和 delegated。
- 应用访问控制。
- 应用角色、scope、permission code。
- 登录日志和授权日志。
- Java 与前端示例应用。

### 9.2 第二阶段：企业兼容能力

- SAML IdP。
- CAS Server。
- LDAP/AD 对接。
- 企业微信、钉钉、飞书登录。
- 开发者门户。
- 接入测试工具。

### 9.3 第三阶段：安全治理

- MFA。
- 策略引擎。
- 在线会话管理。
- Token 撤销和重放检测。
- 风险事件。
- 密钥轮换。
- 审计报表。
- centralized 基础能力，包括菜单、按钮、API 资源托管。
- 权限判定接口和 permission_version 缓存失效机制。

### 9.4 第四阶段：平台化能力

- 多租户。
- SCIM。
- SIEM 对接。
- Webhook。
- SDK 体系。
- 高可用部署模板。
- 权限中心增强。
- 数据权限和 hybrid 完整能力。

## 10. 主要风险

- 自研协议导致安全漏洞和接入困难。
- 登录、权限、业务授权边界不清，导致系统复杂度失控。
- 过早做强权限中心，增加业务系统接入阻力。
- 对 LDAP、短信、第三方 IdP 等外部依赖缺少降级策略。
- 审计日志后补，导致安全合规能力缺失。
- 没有开发者门户，导致平台组长期被接入问题拖住。

## 11. 评审关注点

- 协议范围是否满足公司现有系统接入需求。
- 身份源和组织架构是否符合公司 HR/AD 现状。
- 权限中心采用轻模式还是强模式。
- MFA、密码、会话和 Token 策略是否符合公司安全要求。
- 高可用目标和运维投入是否匹配。
- 第一批试点应用选择是否合理。
